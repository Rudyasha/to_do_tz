# Приоритеты и риски

## 1. Какие три функциональные области или сценария я считаю наиболее критичными для пользователя? Почему?

### 1. Управление жизненным циклом таски

В первую очередь я бы проверяла основной пользовательский сценарий:

Создание задачи > редактирование > изменение статуса > удаление

Тк это ключевая функциональность Todo приложения. Юзер должен быть уверен, что создал именно одну задачу, редактируется и удаляется именно выбранная задача, и ее состояние корректно меняется после каждого действия + здесь для меня особенно важны не только отдельные CRUD операции, но и их последовательность. Напр, созданную таску можно сразу отредактировать, отметить выполненной и удалить без нарушения состояния списка.

### 2. Согласованность состояния задач и фильтрации

Фильтры All / Active / Completed напрямую зависят от текущего состояния задач, поэтому если юзер отмечает задачу выполненной в разделе Active, она должна исчезнуть из Active, появиться в Completed и при этом оставаться доступной в All.

Поэтому я бы обязательно проверяла комбинации:

- изменение статуса + переключение фильтра;
- создание задачи + фильтрация;
- удаление задачи из разных фильтров;
- редактирование задачи с последующей сменой фильтра.

### 3. Взаимодействие приложения с API и обработка промежуточных состояний

Тк основные операции зависят от внешнего API, считаю критичными сценарии с задержкой и ошибкой ответа. Поэтому проверяла бы не только успешный ответ, но всю цепочку:

Действие юзера > HTTP request > response > изменение состояния интерфейса.

Например, если юзер нажал checkbox, но PUT запрос завершился ошибкой, интерфейс не должен создавать впечатление, что изменение успешно сохранено.

То же относится к Create, Edit и Delete: при задержке до 2 секунд юзер не должен случайно отправлять одно действие несколько раз, а при ошибке запроса приложение должно оставаться в понятном и консистентном состоянии + отдавать корректное состояние юзеру

## 2. Какие проверки я бы отложила на последнюю очередь, если до релиза оставался 1 час? Почему?

При таком ограничении времени я бы использовала risk-based подход.

Сначала я бы проверила критический пользовательский путь:

Загрузка списка > создание > редактирование > изменение статуса > фильтрация > удаление.

Дополнительно я бы проверила основные API запросы в Network и хотя бы один сценарий с задержкой или ошибкой API.

На последнюю очередь я бы оставила:

- незначительные визуальные расхождения: отступы, цвета, hover-состояния;
- редкие cosmetic cases с очень длинным текстом, если они не ломают layout и функциональность;
- глубокую проверку разных размеров окна;
- повторное покрытие уже проверенных happy-path сценариев разными похожими тестовыми данными;
- окружения и браузеры.

Причина в приоритете влияния на пользователя. Ошибка в Create, Edit, Complete или Delete мешает использовать продукт по назначению. Небольшое визуальное отклонение обычно не блокирует основной сценарий и может быть исправлено позже.

## 3. Какой неочевидный риск я вижу с учетом JSONPlaceholder?

Основной риск я вижу в рассинхронизации между состоянием интерфейса и реальным состоянием данных.

JSONPlaceholder имитирует POST, PUT и DELETE, но изменения не сохраняются постоянно.

Из-за этого успешный HTTP response еще не означает, что данные действительно сохранены.

Например:

Пользователь удаляет задачу > DELETE завершается успешно > frontend удаляет задачу из списка > пользователь обновляет страницу > GET снова возвращает исходную задачу.

То же возможно после редактирования или изменения статуса.

Более неочевидная проблема появится при повторной загрузке данных, например при будущей пагинации или infinite scroll. Если приложение смешивает локально измененные данные с повторно полученными данными JSONPlaceholder, удаленная / измененная задача потенциально может снова появиться в интерфейсе либо состояние списка станет противоречивым.

Поэтому для этого продукта я бы отдельно проверяла consistency между client state и данными, которые приходят после повторного GET, а не считала успешный POST/PUT/DELETE достаточным подтверждением корректности операции.
